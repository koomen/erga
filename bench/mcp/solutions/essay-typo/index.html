Summary

Fieldbook is the app our customers' inspectors use to record site visits: a checklist, photos, measurements and a signature at the end. Today the app needs a network connection for almost every action. Inspectors work in basements, plant rooms, tunnels and rural sites where the signal is weak or absent, and they lose work when a request fails halfway through a form.

This document proposes an offline-first data layer for the mobile app. Every change is written to a local database first and synced to the server in the background. The inspector never waits for the network, and a visit recorded with no signal at all is uploaded the next time the phone is online.

The work takes about two quarters for three engineers. The first release ships offline checklists and photos; the second adds offline creation of new sites and assets.

Background

Fieldbook started as a thin client over our REST API. Each screen loads its data when it opens and saves when the inspector taps Save. That design was cheap to build and kept the app small, and for the first two years most of our customers were property managers who inspected offices with good Wi-Fi.

The customer base has changed. Since last year, utilities, rail operators and agricultural co-operatives make up more than half of new contracts. Their inspectors spend most of the day out of coverage. Support tickets tagged connectivity grew from 4% of all tickets in January to 19% in September, and they are the most common reason a customer gives when a renewal is at risk.

We tried two short-term fixes. In March we added automatic retries with exponential backoff to every save. In June we added a draft cache that keeps the current form in memory if a save fails. Both helped with brief drops, but neither survives the app being closed, and neither lets an inspector open a site they have not already loaded.

"My people do the job, come back to the truck, and find half the morning's photos never made it. They do the visit again. That is a day lost every week." — Operations manager at a regional water utility

Goals

  • An inspector can complete every step of an inspection with no network: open a site, fill a checklist, take photos, sign, and submit.
  • No work is lost when the app is closed, the phone restarts, or the battery runs out mid-visit.
  • Work done offline reaches the server within one minute of the phone getting a usable connection.
  • Office staff see a clear status for each visit: recorded on the device, uploading, or complete.
  • The sync engine is generic: new record types reuse it without new sync code.

Non-goals

  • Real-time collaboration between two inspectors on the same checklist. Two people rarely edit one visit, and the rules in Conflict resolution cover the rare case.
  • Offline access to the web dashboard. Office staff work at desks with reliable connections.
  • Peer-to-peer sync between devices on a site with no internet.
  • Changing the server's REST API for third-party integrations. Partners keep the endpoints they use today.

The current system

The app is written in React Native. Screens fetch data through a small client library, api-client, that wraps fetch with authentication and retries. There is no persistent local store: the only on-device state is the session token in the keychain and the draft cache added in June.

On the server, a visit is a row in visits with a JSON column for answers, plus rows in photos that point to objects in blob storage. Each save replaces the whole JSON column. The server takes the last write it receives, so two saves that arrive out of order can lose an answer, and we have seen this happen in the field when retries overlap.

The web dashboard reads the same tables through the same API. Office staff use it to assign sites to inspectors, review submitted visits and export reports. It polls for new visits every 30 seconds, which is why a visit submitted from the field appears on the dashboard within half a minute when the network works, and why office staff call inspectors to ask where a visit is when it does not.

Three partner integrations read visits through the public API: two asset-management systems and one compliance archive. They fetch submitted visits by date range every night. Whatever we change on the device, the shape of a submitted visit in that API must stay the same.

What breaks offline

  1. Opening a site the inspector has not opened before: the site, its assets and its checklist template all come from the network.
  2. Saving answers: each save is a request, and a failed save leaves the form in an unknown state.
  3. Photos: the upload starts when the photo is taken and is cancelled if the inspector leaves the screen.
  4. Signing and submitting: the server validates the visit and returns the PDF report, so both need the network at the very end, which is exactly when inspectors are often furthest from coverage.

Proposed design

The app gets a local database, an outbox of changes, and a sync engine that runs whenever the phone is online. Screens read and write only the local database. They never call the network themselves.

Components

  • Local store. SQLite through op-sqlite, with one table per record type and a generic changes table for the outbox.
  • Repository layer. Typed functions such as saveAnswer(visitId, questionId, value) that write to the store and append a change in one transaction.
  • Sync engine. A background task that pushes the outbox in order, pulls changes from the server since the last cursor, and applies them to the store.
  • Blob queue. A separate queue for photos and signatures, because files are large and should not block small changes behind them.
  • Status service. A small module that exposes the state of each visit to the UI: local, pending, or synced.

The server gains two endpoints: POST /sync/push, which accepts a batch of changes, and GET /sync/pull?cursor=…, which returns changes after a cursor. The existing endpoints stay for the web dashboard and for partners.

The life of one answer

  1. The inspector taps Fail on question 12 of a pump inspection.
  2. The screen calls saveAnswer, which writes the answer row and appends a change to the outbox in one SQLite transaction.
  3. The screen re-renders from the store at once and shows the answer with a small grey dot: recorded on this device.
  4. Two seconds later, if the phone is online, the sync engine pushes the outbox. The server applies the change and answers with the new version.
  5. The engine removes the change from the outbox and updates the answer's version. The dot disappears.
  6. If the phone is offline, nothing else happens until the network comes back. The answer is safe in the store whether the app is closed, killed or restarted.

Authentication offline

Session tokens expire after twelve hours today, which would lock an inspector out of a two-day trip to a remote site. The app will keep a refresh token in the keychain, valid for 30 days, and treat an expired session token as "sign in again when online" rather than "sign out now". The inspector keeps working with the data already on the device. If an administrator disables a user, the next successful sync wipes that device's store after pushing its outbox, so no work is lost and no data stays behind.

Screens never wait for the network. A save is complete when the local transaction commits, which takes a few milliseconds even on old phones.

Data model

Every synced record has a client-generated ID (a UUIDv7, so IDs sort by creation time), a version number, and a updated_at timestamp from the device clock. The server keeps its own server_seq, a monotonically increasing number that defines the order of changes for pull.

We split a visit's answers out of the JSON column into one row per answer. This makes each answer an independent unit for sync and conflict resolution, and it lets two inspectors fill different parts of the same checklist without clobbering each other.

Versions and history

Each record's version starts at 1 and goes up by one with every change the server applies. A change carries the version it was based on, which is how the server detects a conflict. The server also writes every applied change to an append-only record_history table, keyed by record and version, with the device, the user and both clocks. The history is what lets a reviewer see a value that lost a conflict, and it gives support a full trail when a customer asks who changed an answer and when.

History is kept for two years, then compacted to one row per record per day. The compaction runs on the server only; devices never hold history, which keeps the local database small.

Deletions

A deleted record becomes a tombstone: the row stays with a deleted_at time and no other fields, so that the deletion syncs like any other change. Devices drop tombstones after they have applied them and their cursor has moved past them. The server keeps tombstones for 90 days, which is longer than any device should stay offline; a device whose cursor is older than that does a full resync of its regions instead of a pull.

Templates are read-only on the device. They are pulled like any other record, but the device never pushes a change to one.

Sync protocol

Sync is a loop of push, then pull. Push sends the outbox in the order the changes were made, in batches of up to 200. The server applies each change in its own transaction and answers with one result per change: applied, applied with a conflict resolved, or rejected with a reason.

POST /sync/push
{ "device": "d-81f3", "changes": [
  { "id": "c-0192…", "table": "answers", "key": ["v-77a1", "q-12"],
    "patch": { "value": "pass" }, "base_version": 3 }
] }

Pull asks for every change after the device's cursor, filtered to the regions the inspector is assigned to. The server returns at most 500 changes and a new cursor; the device keeps pulling until the server says there is nothing more. The device applies pulled changes in one transaction per batch, so the store is never half-updated.

Photos and signatures

Files upload through the blob queue, in a separate background task from the change outbox. Each file gets a pre-signed upload URL from the server, uploads in 5 MB parts so a dropped connection loses at most one part, and is confirmed with a small change in the outbox once the last part is stored. The visit can be submitted before its photos finish uploading: the server marks the report as awaiting files and completes it when the last file arrives.

Failures and retries

A push or pull that fails because of the network is retried with backoff: 2 seconds, then 4, 8 and so on up to 5 minutes, with random jitter so that a whole team coming back into coverage at the end of a shift does not hit the server at the same moment. A change the server rejects is not a network failure and is never retried. A server error (a 5xx answer) is retried like a network failure, but after ten failures in a row the engine stops, reports the error with the sync log, and waits for the next app start.

Pushes are idempotent. Each change has its own ID, and the server remembers the IDs it applied for 30 days, so a push that timed out after the server applied it can be sent again safely.

When sync runs

  • When the app starts or comes to the foreground.
  • Within two seconds of a local change, if the phone is online.
  • When the operating system reports that the network came back.
  • Every 15 minutes in the background, when the operating system allows it.

Conflict resolution

A conflict happens when the server has a newer version of a record than the version a change was based on. Because answers are one row each, conflicts are rare: they need two people to answer the same question of the same visit while at least one of them is offline.

The rules, in order:

  1. A visit's status only moves forward (draft, then submitted, then reviewed). A change that would move it back is rejected.
  2. For an answer, the later change by device clock wins, and the server keeps the losing value in the answer's history so a reviewer can see it.
  3. A deletion wins over an edit of the same record, unless the edit is newer by more than ten minutes.
  4. Photos never conflict: each is a new record with its own ID.

An example

Ana and Ben inspect the same substation. Ana answers question 7 "fail" at 10:02 in the basement, with no signal. Ben, upstairs with signal, answers the same question "pass" at 10:05, and his change reaches the server at once. Ana comes back into coverage at 11:30 and her change arrives, based on the version before Ben's. Ben's change is later by device clock, so it stays; Ana's "fail" goes into the answer's history, and the reviewer sees both with their times. Ana's app shows her the answer that won, with a note that Ben changed it.

Device clocks drift. The device sends its clock with every push, and the server stores the offset between the device clock and its own. When it compares two changes, it uses device time corrected by that offset.

When a change is rejected, the device does not retry it. It marks the record with a warning that the inspector sees on the visit, with the reason in plain words, such as "This visit was already reviewed by the office, so the answer was not changed."

Performance budget

The offline store must make the app faster, not slower. We measured the current app on our lowest supported device, a four-year-old mid-range Android phone, and set budgets for the new design.

ActionToday (good signal)Budget, offline store
Open a site's visit list1,400 ms150 ms
Save one answer620 ms20 ms
Take and attach a photo2,100 ms300 ms
Submit a visit3,800 ms100 ms
First sync of a region (2,000 sites)n/a45 s

The first sync of a region is the only slow step, and it happens once per device. It downloads a compressed snapshot of the region, prepared by the server every night, and then pulls only the changes since the snapshot. Without the snapshot, a first sync of 2,000 sites took over six minutes in our prototype because of the number of small pull pages.

The database for one region of 2,000 sites, with their assets and the last year of visits, is about 60 MB without photos. Photos stay on the device only until the server confirms they are stored, and then for seven more days as a cache.

Rollout plan

We roll out in two releases, each behind a remote feature flag, so we can turn the offline store off for a customer without a new app version.

Release 1: offline visits

  • Local store, repository layer and sync engine for sites, visits, answers and photos.
  • Internal dogfood for three weeks with our own field team, who inspect the office buildings we lease.
  • Beta with two customers who volunteered: a water utility and a rail maintenance contractor.
  • General availability when the beta shows no lost visits for four weeks in a row.

Release 2: offline assets

  • Create and edit assets offline, with the same conflict rules.
  • Remove the old save endpoints from the app; the server keeps them for the web dashboard.

How we will know it works

  • Lost visits: visits started on a device that never reach the server within 7 days. The target is zero, and every one is investigated.
  • Sync latency: the time from a change being made with a usable connection to the server applying it. The target is under one minute at the 95th percentile.
  • Outbox age: the oldest unsent change on each device, reported with each sync. A device with a change older than three days gets a support follow-up.
  • Connectivity tickets: the share of support tickets tagged connectivity, which we expect to fall below 5% within a quarter of general availability.

Testing

The sync engine gets a test harness that runs two simulated devices and a real server against each other, with a network that can drop, delay and reorder requests. Every conflict rule has a test in this harness. We will also run a weekly "basement day", where the team takes test phones into the car park's lowest level and completes ten scripted inspections with no signal.

Every inspector's device migrates its draft cache into the new store on first launch. If the migration fails, the app keeps the draft cache, reports the error, and turns the flag off for that device.

Alternatives considered

A sync product

We evaluated two hosted sync products. Both would cut the engine's build time roughly in half. We rejected them because they need their own server-side database as the source of truth, which would mean moving or mirroring our Postgres data, and because their per-device pricing would cost more than the team building it within eighteen months.

Keep the REST API and add a request queue

The smallest change would be to queue failed requests on the device and replay them later. It does not let an inspector open a site they have never loaded, it keeps the last-write-wins problem on the JSON column, and replaying requests in the right order after the app restarts is most of the work of an outbox anyway.

CRDTs for answers

A CRDT would merge concurrent edits without a rule for who wins. Answers are single values (pass, fail, a number), so merging them has no meaning: one of the two values must win. A CRDT would add a library and a storage format for no gain over the rules above.

Risks

  • Storage on old phones. Some inspectors' phones have under 2 GB free. The app will warn at 500 MB free and stop caching photos it has already uploaded.
  • Background limits. iOS may run background sync rarely. Inspectors must open the app once with a connection after a shift, and the app reminds them with a local notification.
  • Schema changes. A change to a synced table now needs a migration on every device as well as on the server. We will version the local schema and refuse to sync from an app that is too old.
  • Security of data at rest. A lost phone now holds a region's sites and visits. The store will be encrypted with a key kept in the keychain, and an administrator can wipe a device remotely from the dashboard.
  • Duplicate visits. An inspector who cannot see a visit started by a colleague may start a second one for the same site. The dashboard will flag two visits for the same site on the same day so the office can merge them.
  • Support load during the beta. Sync problems are hard to debug from a ticket. The app will include a "send sync log" button that uploads the last 1,000 sync events.

Open questions

  • Should a region's first sync happen over mobile data, or only over Wi-Fi by default? 60 MB is a lot on some customers' data plans.
  • How long should the device keep visits that were submitted and reviewed? We propose one year, matching the dashboard's default filter.
  • Do customers need to receive a notice when an inspector's answer loses a conflict, or is the answer's history enough?
  • Should the sync engine be shared with the planned web dashboard's offline mode, if that project goes ahead next year?
  • Who owns the sync endpoints on the server: the mobile platform team or the core API team?
